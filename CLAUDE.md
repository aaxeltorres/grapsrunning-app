# Graps Running App

iOS beta prototype of the Graps Running mobile app. React Native + Expo (SDK 57) + TypeScript.
Mobile companion to the web project in the `grapsrunning` and `grapsrunning-backend` repos.
All UI text is in English.

## Vision (where the app is going)
A running app in the style of Nike Run Club / Adidas Running / Strava, with a virtual AI coach called **Mike**:
- Motivates the user: push notifications and voice while running.
- Greets the user by name when opening the app ("Hola <name>").
- Follows up when the user misses a training day.
- Generates a personalized training routine, shown in the Plan section.

Implemented today: fake auth/sign-in, Home dashboard, Stats, the run mode selector (opened by Start run on Home: Quick start, Set a goal, Intervals and Today's workout; without a workout waiting, or with today's one done, a sheet offers a free run), Intervals (a light setup screen to build your own workout: warm-up, up to four blocks of reps and sets, each with its work by distance or time, zone, rest between reps and sets, quick presets, a live estimate, GPS-rule notes and the last setup remembered; it runs like a plan workout, as a free run that never touches the Plan, and its results show the reps), goal runs (setup screen where any two of distance, time and pace are set and the third is derived, with range limits and valid one-tap fixes; a goal run view with progress bars and silent red off-track alerts; met / missed goals on Run results), GPS run tracking (background location), the Active Run shell (fades to dark while running and back to light while paused) with a view per run mode (basic, goal, and plan workouts run step by step, each by its type: zone chip and target pace on every step, countdown by time or distance with "Rep i of n" / "Set j of m", calm rests with a preview of the next rep and a set summary in macro rests, manual steps with an elapsed timer and a large Done / Ready button, distance as the hero in Z2 sessions, zone and time left with a zone timeline in tempo / progressive sessions, silent pace alerts by zone (Z1-Z2 only when too fast) with quicker timing on short steps, step haptics (rep start, rest start, 3-2-1), whole-workout bar, skip; started from Start workout on the Plan or Today's workout, with edits included; finishing marks the workout completed, or partial when cut short, and stores the actual stats), Run results (distance hero, time / pace / calories, route map or an empty state, per-kilometer splits, a short-run state, goal results, planned vs actual for plan runs, the reps of a structured workout against their targets; sections fade in one after another), the Plan onboarding (Mike's scripted first-visit chat that builds the runner profile, including the plan length: one week at a time or a full month), the Plan screen (Week / Month views of a 4-week monthly plan, or only the week view of a weekly plan, which gets its next week added when that week starts and the app opens; six categories by color: Easy, Aerobic, Tempo, Long, Intervals, Speed; the card shows the session name, e.g. Fartlek or HIIT, its structure in coach notation and its top zone, plus a Zones link to the zone guide sheet; finished days are marked with a check in the workout color, and a finished workout's card shows the actual stats and a "Run again freely" link), structured sessions assigned by the generator (regenerative, extensive aerobic, progressive, tempo run, strides, fartlek, mixed and long intervals, HIIT, HIIT in sets, sprints; zones Z1-Z5 by pace; sets with macro rests; manual Done / Ready steps for what GPS can't measure), the Your profile screen (opened from the gear on the Plan screen: change any onboarding answer, and on leaving, a sheet offers Create a new plan (rebuilds every planned workout from today on, edited ones included; finished and skipped ones stay; a short "building your plan" state of at least 1.2 s, then back to the Plan screen, where Mike announces it; if it fails, an error state with Try again / Not now keeps the old plan) or Keep current plan, shown only when the plan answers differ from the ones the saved plan was built from, and a "Create a new plan" row at the bottom does the same on demand after a confirmation, through the same function and the same loading state; plus the "Intensity by" setting, Pace only, Heart rate coming soon) and the workout editor (opened from Edit on the workout card: a free-scrolling run type carousel with every session (native horizontal scroll that snaps to the centered tile) and a draggable duration bar that follows the finger; saved workouts are marked `edited`).
Not implemented yet (Home cards exist as placeholders): AI Coach chat, Routes. Plans are mock data from `generatePlan`. A monthly plan is not renewed after its four weeks yet, and weekly plans continue the pattern with no adaptation to what was run. The workout editor can't move a workout to another day or add one on a rest day yet, and edits a session only by its total time (editing its reps, sets and zones is a follow-up). The coach's warm-up drill routine (as a text note) is not added yet. Zones are by pace only: there is no heart rate. Nothing consumes the workout events yet (Mike's voice will).

## Commands
- Install: `npm install`
- Dev server: `npx expo start` (or `npx expo start --tunnel` to test from another network)
- Typecheck (must pass before finishing any change): `npx tsc --noEmit`
- Background location needs a development build; it does not work in Expo Go.

## Project structure
- `src/theme`: design tokens (colors, typography, spacing). Use them; do not hardcode values.
- `src/components`: reusable UI components
- `src/screens`: app screens
- `src/navigation`: navigation and route types
- `src/hooks`: shared hooks, including run tracking and the chat engine (`useChatReveal`, which hands out stable `displayItems`; `OnboardingChat` memoizes each message group and follows the conversation with one post-layout scroll per new entry, never while the user is dragging or has scrolled up)
- `src/coach`: Coach Mike's scripted conversations, pure TypeScript (no React)
  - `planOnboardingScript.ts`: the Plan onboarding script. All of Mike's copy, questions, options and reactions live here.
  - `types.ts`: script step types (message, question, recap).
  - `conversation.ts`: builds the chat transcript from the script plus the saved answers (resume, edits, recap).
  - `runnerProfile.ts`: the `RunnerProfile` model. Stores stable option ids and metric values, never display labels. `planLength` ('weekly' / 'monthly') is a plan answer: read it with `planLengthOf` (missing means monthly; `usePlanOnboarding` records 'monthly' on profiles that finished the onboarding before the question), and changing it adds a line about it to the Your profile sheet (`planLengthChanged`). `planAnswersSnapshot(profile)` is the normalized form of the plan answers (goal, level, speed work, days, plan length, injuries; order-insensitive) and `samePlanAnswers` compares two. `intensityBy` is a setting (missing means pace), not a plan answer. `LevelId` has eight levels, the top three being `run_half`, `run_marathon` and `run_competitive` (advanced like `run_10k_plus`, each with its own easy pace in `EASY_PACE`, same volume and rep numbers as `run_10k_plus` for now); read a saved level with `knownLevel`, which returns `undefined` for an id this version doesn't know (treated as no level by `rulesFor` and `planAnswersSnapshot`).
  - `plan.ts`: the `Plan` / `Workout` model (dated workouts made of steps and repeat groups; meters, seconds, seconds per km; a run workout has status `completed` / `partial` and an optional `result`, with optional per-rep `reps`, all additive so old saved plans still load; `Plan.length` is 'weekly' or 'monthly', missing means monthly, and `weeks` counts the weeks generated so far; `basedOn` is the plan answers it was built from and `keptAnswers` the ones the user kept it for, and `planNeedsRebuild(plan, answers, fallback)` is the rule behind the Your profile leave sheet: it shows only when the answers equal neither, with the profile as it was when Your profile opened as the fallback for plans without `basedOn`). Also additive: `type` is the category (easy, aerobic, tempo, long, intervals, speed, rest) and `session` the specific session; a step may have a `zone` (1-5) and a `manual` target (ends on Done / Ready); a repeat group may have `sets`, a `macroRest` and `noFinalRest` (no rest after its very last rep). Step kinds: `recovery` is the micro rest, `macroRest` the rest between sets, `steady` continuous running. Pure helpers: `unrollSegments` (the one unrolling of reps and sets, with indices), `totalDistance`, `totalDuration`, `displayName`, `structureLine`, `topZone`, `isDemandingType`... Plain JSON, so an AI can produce it.
  - `generatePlan.ts`: `generatePlan(profile, today, { weeks })` returns a deterministic rule-based mock plan (four weeks for a monthly plan, one for a weekly plan); the AI integration goes here and in `generateWeek`. `extendPlan` adds the current week to a weekly plan once it starts (by its calendar week index, so the pattern continues; weeks the app was not opened in stay empty; existing workouts are never touched). `generatePlan` and `extendPlan` stamp `Plan.basedOn` (the plan answers the plan was built from; an extension clears `keptAnswers`). `createNewPlan(plan, profile)` is the only way to rebuild a plan (the Your profile row and its leave sheet both call it) and replaces every planned workout from today on (edited too) and keeps the rest, with no duplicate dates. Its rules: no demanding sessions (long, intervals, speed, tempo) on consecutive days, interval-type sessions only with speed work, advanced sessions from the 5K level up (`isAdvancedLevel`, including the half, marathon and competitive levels), beginners and runners in pain keep run/walk / easy plans. Weeks come in blocks of four (build, build, build, lighter): each week's total time follows `WEEK_CURVE` (1, 1.08, 1.16, 0.92 of week 1; +5% per later block, up to +20%), fitted by one load `s` per week (`fitWeek`: session flex parts, easy and regenerative runs, gentle minutes, beginners' run bouts) that keeps build weeks within 0 to +10% of the week before and the fourth week 15-25% below the third, in time and distance; the long run has its own curve (`LONG_CURVE`, shorter in week 4), beginners drop a rep in week 4, and the longest quality session sits in week 3. Sessions and classic intervals take their variant from the week, so a session never repeats with the same structure on the same weekday in consecutive weeks. The 10K level and up (not beginners, not in pain) have their own volume (`LEVEL_VOLUME`, with `GOAL_VOLUME` by goal id; `Rules.volume`): week 1 is fitted to minutes per training day × days × the goal factor (`fitFirstWeek`, capped so the build weeks can still grow), the week-1 long run sits between the level's floor and ceiling by goal (10K level: at least 10 km; capped at 32 km and the editor's 180 min), sessions get `extraReps` and a bigger `SESSION_LEVEL_SCALE` and stay within `SESSION_SPECS`, classic intervals within 75 min and easy runs within 120 min; they fit on a wider load grid (`fitLoads`). Levels below 10K keep the original path, unchanged. A block builds base volume only: no peak, taper, race date or race-pace work.
  - `sessions.ts`: the templates of each structured session in variants (reps, rep length or zone split; `SESSION_SPECS`: category, speed work, advanced, editor limits) and `buildSession`, which scales the continuous parts to a total time and leaves rep blocks fixed; `variant` (the plan week) picks the variant, and `extraReps` adds reps to each rep block for the strong levels (`sessionExtraReps`, passed by the generator and the editor alike). Shared by the generator and the editor, which rebuilds a session with its week's variant.
  - `zones.ts`: zones Z1-Z5 (name, feel) and their pace ranges from the easy pace, clamped to the app's pace limits. By pace only: no heart rate yet.
  - `workoutEditor.ts`: pure logic of the workout editor (run types including every session, limits, warm-up / main / cool-down layout, the workout built from a draft, the hard-session warning; `layoutTable` builds every amount's layout once per run type, so the duration bar's drag never rebuilds a session). Built on the generator's rules and paces; sessions are edited by total minutes.
  - `planOnboardingScript.ts` also asks the plan length (after the training days).
  - Mike's Plan screen one-liners (`planDayMessages`) and his workout editor lines (`editorMessages`) also live in `planOnboardingScript.ts`.
  - Scripted chats are not connected to the AI chatbot, and every answer is a predefined option (no free text).
- `src/run`: pure logic of the run flow (no React)
  - `runModes.ts`: run mode ids (quick, goal, plan, intervals) and their names / descriptions (placeholders, one place to rename them).
  - `intervalConfig.ts`: every number of the Intervals setup (blocks, reps, sets, wheel values, rest and total limits, manual-step estimates).
  - `intervalSetup.ts`: the `IntervalSetup` model (warm-up, cool-down, up to four blocks; plain JSON), presets, `normalizeSetup`, `buildIntervalWorkout` (the setup as a normal `Workout`, with the model's GPS rules through `paceFor`: under 30 s no pace, under 100 m a manual Done step), `setupStats`, `validateSetup` and `blockNote` (the one-line GPS explanation).
  - `todayWorkout.ts`: `todayRunState(plan, today)`: planned / completed (also partial) / rest / none, for the mode selector.
  - `types.ts`: `RunViewProps`, what the ActiveRun shell hands to every run view.
  - `goals.ts`: the `RunGoal` model (optional distance, time, pace) and pure helpers: the setup model (`GoalSetup`: at most two goals the user sets, the least recently set one becomes the derived third), validate (ranges, impossible derived values), `goalFixes` (one-tap fixes, only valid ones), progress, reached, met / missed results, formatting.
  - `goalAlerts.ts`: off-track alert state machine (smoothed pace, target pace or pace range, projected finish, hold / clear debounce, start grace; optional fast-side-only alerts and custom timing). Shared by goal runs and plan workout runs.
  - `goalConfig.ts`: every goal-run number in one place (limits, presets, pace tolerance, smoothing window, alert timings), and every alert number of plan workouts too (per-step grace, short-step window / hold / clear / grace).
  - `stepBehavior.ts`: how the run screen treats each plan step: `segmentAlertTargets` (no alert on rests, manual or unmeasurable steps; Z1-Z2 fast side only; short steps under 2 min use the quick timing), `sessionStyle` / `stepLayout` (manual, rest, distance, zone block, countdown), `zoneTimeline`, `nextWork` and `countdownTicks` (the 3-2-1 before a timed rep).
  - `repResults.ts`: records every work step from the engine events (time, distance, pace only when measurable, how it ended), `setSummary` for macro rests and `repRows` for Run results.
  - `workoutSegments.ts`: `buildRunSegments(workout)` unrolls a plan `Workout` (steps, repeat groups, sets and macro rests, through `unrollSegments`) into ordered run segments: target, pace range (none when GPS can't measure it), rep and set counters, micro / macro rest, zone, how it ends (`auto`, `done`, `ready`), label, color tone. No second workout model.
  - `workoutEngine.ts`: executes the segments on moving time and distance: auto-advance by time or distance (handovers placed between ticks), `confirmSegment` for manual Done / Ready steps, skip, finish early, remaining amount and overall position.
  - `workoutEvents.ts`: segment start / end (reasons: completed, done, ready, skipped, finished), km split and workout complete events, and a tiny event bus for a future coaching layer.
  - `planResult.ts`: connects a finished plan run back to the Plan: `buildWorkoutResult`, `recordWorkoutRun` (marks a planned workout `completed` or `partial` with its result; never overwrites a first result), `workoutActuals` (the real numbers, or the plan's for old records) and `plannedVsActual` (rows for Run results). ActiveRunScreen records the run through `planStorage.update`.
  - `workoutConfig.ts`: plan-workout run numbers (the 3-2-1 length) and what GPS can measure: no pace target under `MIN_PACED_EFFORT_S` (30 s), sprints under `MIN_MEASURED_DISTANCE_M` (100 m) are manual.
  - `splits.ts`: `computeSplits` (per-km splits from the timestamped route: pauses removed, crossing times interpolated, last partial row), `fastestSplitIndex`, `splitBarFraction` and `isRunTooShort` (the rule behind the short-run state). ActiveRunScreen computes the splits and passes them, with the start time and calories, to RunResults.
  - ActiveRunScreen is the shell (owns `useRunTracking` and the theme fade: dark while running, light while paused); `BasicRunView`, `GoalRunView` and `PlanRunView` in `src/components` are the views. `useGoalAlerts` (src/hooks) feeds `goalAlerts.ts` from the tracking ticks; `useWorkoutRun` drives the workout engine, its per-step pace alert, the rep recording, the step haptics and its events for `PlanRunView`, which draws `WorkoutProgressBar` and `ZoneTimeline` and shares `AlertBlock` with `GoalRunView`. `GoalSetupScreen` + `GoalPickerSheet` build the goal (the hint, its fixes as `Chip`s and Start are pinned in the footer; only the cards scroll); `ZoneGuideSheet` (opened from the workout card's Zones link, hosted by `PlanOverview`) explains the zones with the runner's paces. `PlanBuildingView` is the full-screen "building your plan" / error state of Your profile (a plain overlay, never a Modal; static text with Reduce Motion): ProfileScreen never navigates while a sheet (a Modal) is still closing, it waits for the sheet's `onClosed` plus a frame, because leaving under a presented Modal can leave the next screen untouchable. `IntensitySheet` is the shared "Intensity by" sheet (Pace selected, Heart rate disabled as coming soon), opened from the "Intensity by" row of Your profile and of the Intervals setup. `GoalResultsSection` is the self-contained goals block on Run results and `PlanComparisonSection` the planned-vs-actual block of a plan run, followed by `RepResultsSection` (the reps, when the workout had any: a plan workout or an interval run, which has no planned block). `IntervalSetupScreen` builds the interval workout from `IntervalBlockCard`s (one per block: work by distance or time, reps, zone chips, rests, sets) and a shared `IntervalPickerSheet` (wheels, "Until I'm ready" on the rests); it reuses `ZoneGuideSheet`, runs it through `ActiveRun` mode `intervals` (`PlanRunView` with a `title`, no `recordPlanRun`) and saves the setup when Start is pressed. Run results is an ordered list of sections (hero, stats, `RunRouteCard`, goals, `RunSplits`) faded in by `useStaggeredEntrance`; a new section (e.g. planned vs actual) is one more entry in that list. Mike's selector lines (`runModeMessages`) live in `planOnboardingScript.ts`.
- `src/storage`: persistence behind small modules with get / save / clear, backed by AsyncStorage for now. `profileStorage` keeps the runner profile, `planStorage` the training plan (`update(change)` is a read-modify-write used to record a finished run), `intervalStorage` the last Intervals setup (normalized to the current limits when read). Each is the only file to change when that data moves to a real database. `planSync.ts` (`loadCurrentPlan`) reads the plan and profile, runs `extendPlan` and saves the result: `usePlanOnboarding` calls it on load and on every Plan focus, and `RunModeScreen` for Today's workout.
- `src/tasks`: background tasks
- `src/utils`: formatting, calendar dates (`dates.ts`, local `YYYY-MM-DD`), location, haptics, the wheel picker's row math (`wheel.ts`: a row is `round(offset / ROW_HEIGHT)`, `nearestRow`, the slow-release rule; pure, used by `WheelPicker`) and mock-data helpers. `mockRun.ts` holds mock finished runs (long, goal, short, no route, plan, partial plan) to preview Run results without running; nothing imports it.
- `dist/` and `.expo/` are generated. Never edit them.

## Final step (mandatory, every task)

This section applies to EVERY task that changes files in this repo, even when my message does not mention commit, push or version. Not being asked is not a reason to skip it. The only exceptions: I explicitly say "no commit" or "don't push", or the task is only a question or investigation with no file changes.

Run it once the change is implemented and `npx tsc --noEmit` passes. If verification is still incomplete or failing, do not commit: tell me what is missing and ask.

### 0. Check the working tree
Run `git status`. If there are modified files that are not part of this task, do not include them silently: list them and ask me whether to commit them (as separate commits) or leave them out.

### 1. Decide the version bump (semantic versioning, X.Y.Z, each digit goes up to 99)
The single source of truth is `expo.version` in app.json (HomeScreen reads it). Keep `version` in package.json and package-lock.json in sync with it (`npm version X.Y.Z --no-git-tag-version` updates both).
The default is PATCH. Most changes are patches.
- PATCH (x.y.Z): bug fixes, small UI tweaks, copy changes, performance fixes, and improvements or additions inside an existing screen or feature (a new option, a new onboarding question, a new rule, a new component in an existing screen). If Z would pass 99, bump MINOR instead.
- MINOR (x.Y.0): a new user-facing capability as a whole: a new screen, flow or section (e.g. GPS tracking, route map, workout editor). Reset PATCH to 0. Y can go up to 99; do not roll into MAJOR before that.
- MAJOR (X.0.0): breaking or app-wide changes (full redesign, changed data model). Do NOT bump MAJOR on your own: stop and ask me first.
- NO bump: docs, comments, formatting, refactors with no behavior change, tooling/config-only changes.
One bump per task, not per commit. If a task mixes levels, use the highest. When in doubt between PATCH and MINOR, choose PATCH. Never choose MINOR just to "keep the numbers moving".
State which level you chose and why, in one sentence, before touching any version file.

### 2. Commit (clean and easy to understand)
- Review with `git status` and `git diff`. Stage only files related to this change, by name. Never commit secrets, `.env*`, tokens or credentials.
- Use Conventional Commits, written in English: `type(scope): imperative summary` (max 72 chars). Types: feat, fix, refactor, style, docs, chore, perf, test. Example: `fix(active-run): freeze pace while the run is paused`.
- Add a body (wrapped at ~72 chars) that explains WHAT changed and WHY, mentioning the affected screens/components/hooks. Add `BREAKING CHANGE:` when relevant.
- One logical change per commit. If the work has several independent parts, make several commits.
- If the version changed, make a separate final commit: `chore(release): bump version to X.Y.Z` with a body listing which changes justify the bump.

### 3. Push
- Run `git push` on the current branch. Never use `--force`.
- If the push is rejected, run `git fetch` and `git pull --rebase` once and retry. If there are conflicts, stop and tell me instead of resolving them blindly.

### 3b. Publish to Expo (OTA update)
My friends test the app through Expo (branch `preview`), so updates have to be published there.
- Publish automatically after a successful push when the task ended in a MINOR or MAJOR version bump (a big update).
- Publish whenever I ask, whatever the bump size, with phrases like "publish", "publicá el update", "subí a Expo" or "eas update". Never publish on a PATCH or no-bump task unless I ask.
- Before publishing: everything must be committed and pushed, and `npx tsc --noEmit` must pass.
- Command: `eas update --branch preview --message "<subject of the latest commit>" --non-interactive`. Don't ask me for a message; reuse the latest commit subject.
- Do NOT publish if this task changed anything native (app.json plugins, permissions, infoPlist, or a dependency with native code): an OTA update cannot deliver that. Tell me a new build is needed instead.
- Never run `eas build`.

### 4. Report
End with: the old and new version (or "no bump" and why), the commits created (`git log --oneline -n <count>`), the push result, and confirmation that `git status` is clean.
`runtimeVersion` uses the `fingerprint` policy, so a version bump does not affect updates; `eas update` only reaches builds whose native fingerprint matches. Remind me to make a new build only when native code changes (plugins, permissions, infoPlist, native dependencies).
- If an update was published, include the update group ID or link from the command output.

### 5. Update
When you add, move or remove a folder or module, update the project structure section of this file in the same change.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.
`graphify-out/` is generated, local and gitignored: `graphify update .` still runs after code changes, but its output is never committed.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
